# RFC-0003: Finite and Periodic Electronic States

**Status:** Draft for alpha implementation  
**Target:** `ElectronicState` in `ChemIR v1alpha1`  
**Last updated:** 2026-09-02  
**Decision owners:** Core schema, scientific validation, and compute maintainers

## Summary

Finite and periodic electronic states are different models selected by the
required `model` discriminator. A finite state may declare total charge and spin
multiplicity. A periodic state instead declares orbital restriction, collinear
or non-collinear treatment, spin-orbit treatment, and optional magnetization
assertions. Finite electron-count and multiplicity rules must never be applied
to a periodic system.

The alpha schema can preserve both models. Only the finite model is in the
intended first-release normative conformance profile. Periodic electronic-state
readiness remains experimental until its field vocabulary, backend mappings,
units, and scientific corpus pass review.

## Motivation

Using one `charge` and `multiplicity` record for molecules, crystals, metals,
magnetic cells, and spin-orbit calculations creates invalid validation and
misleading UI. A finite entity normally has a defined integer electron count
and total spin multiplicity. A periodic calculation may instead depend on cell
magnetization, initial site moments, collinearity, spin-orbit coupling, electron
smearing, and backend conventions. The two cases need explicit schema and
readiness branches.

## Scope

This RFC defines:

- the `ElectronicState.model` discriminated union;
- required and forbidden fields for finite and periodic states;
- deterministic validation rules;
- the boundary between state intent and backend execution options;
- readiness and diagnostic behavior; and
- alpha decisions that remain open before schema beta.

It does not define wavefunctions, density matrices, excited-state methods,
band occupations, pseudopotential file formats, or a universal magnetic-order
ontology.

## Common contract

`ElectronicState` is a top-level ChemIR object using the RFC-0001 envelope. Its
payload contains:

```json
{
  "target_reference": "molecule:water",
  "model": "finite",
  "charge": 0,
  "multiplicity": 1
}
```

Common rules are:

- `target_reference` resolves to the chemical entity whose electronic state is
  described.
- `model` is exactly `finite` or `periodic`.
- a state is immutable and addressable; a calculation references its exact ID.
- geometry is separate. If a calculation references both a state and a
  `Geometry`, both must resolve to the same target entity.
- asserted fields identify their evidence. Toolkit-derived fields identify the
  toolkit, version, parameters, and derivation evidence and are not silently
  promoted to assertions.
- method, basis, pseudopotential, convergence, k-point, resource, and
  backend-specific flags belong to `CalculationSpec` or a resolved execution
  plan, not to `ElectronicState`.
- optional descriptive fields use omission rather than `null`. The core alpha
  finite state is intentionally complete: charge and multiplicity are required.

The discriminator is semantic and participates in `semantic_hash`. Changing a
state from finite to periodic creates new semantics and invalidates dependent
plans and approvals.

## Finite electronic state

The minimum compute-ready finite payload is:

```json
{
  "target_reference": "molecule:water",
  "model": "finite",
  "charge": 0,
  "multiplicity": 1
}
```

### Fields

| Field | Alpha type | Requirement |
|---|---|---|
| `target_reference` | object reference | Required |
| `model` | literal `finite` | Required |
| `charge` | integer from `-128` through `128`, in units of elementary charge | Required |
| `multiplicity` | positive integer `2S + 1`, at most `128` | Required |
| `state_label` | bounded string | Optional descriptive label; no readiness semantics |

`charge` is the total electronic-state charge, not a partial atomic charge and
not an oxidation state. `multiplicity` describes total spin multiplicity. If an
import lacks either required value, the importer preserves the original
representation and evidence and reports an incomplete state; it does not emit a
schema-valid core `ElectronicState` by inventing a value.

### Electron-count derivation

When the target has a complete finite atom inventory, the validator derives:

```text
electron_count = sum(atomic_number for every atom) - charge
```

Isotope mass does not change atomic number. Ghost atoms, effective-core
potentials, fractional nuclear charges, unresolved atom identities, or another
profile-specific electron convention make the simple derivation unavailable.
The validator records `electron_count` as derived evidence with the rule-bundle
hash; it does not guess.

When an independent, trusted electron-count source exists, a disagreement with
the deterministic derivation is an error. A user cannot override a complete
atom inventory merely by writing another count.

### Finite invariants

For a compute-ready finite state:

1. `charge` is an integer.
2. `multiplicity` is an integer greater than or equal to one.
3. the derived electron count, when available, is non-negative.
4. electron-count parity and multiplicity parity agree:

   ```text
   (electron_count + multiplicity) modulo 2 = 1
   ```

5. a complete formal-charge model on the target is consistent with total
   charge, unless the profile explicitly models ionization as a distinct state
   over a neutral structural target.
6. a complete formal oxidation-state model on a coordination complex is
   charge-sum consistent. Incomplete, fractional, averaged, or alternative
   oxidation-state assignments normally produce review diagnostics, not a hard
   error.

Valence, oxidation-state, geometry, and electron-count heuristics that are not
unambiguous invariants remain warnings. Every stable scientific error rule must
record its basis, applicability domain, counterexamples, severity rationale,
and responsible reviewer.

## Periodic electronic state

The proposed alpha periodic payload is:

```json
{
  "target_reference": "crystal:iron-alpha",
  "model": "periodic",
  "orbital_treatment": "unrestricted",
  "spin_treatment": "collinear",
  "spin_orbit_treatment": "none",
  "total_magnetic_moment": {
    "source_value": 2.2,
    "source_unit": "bohr_magneton/cell",
    "normalized_value": 2.2,
    "normalized_unit": "bohr_magneton/cell",
    "provenance_references": []
  },
  "initial_site_moments": [],
  "magnetic_ordering": "ferromagnetic"
}
```

### Fields

| Field | Alpha values | Requirement |
|---|---|---|
| `target_reference` | reference to `PeriodicStructure` | Required |
| `model` | literal `periodic` | Required |
| `orbital_treatment` | `restricted`, `unrestricted` | Required for readiness |
| `spin_treatment` | `collinear`, `non_collinear` | Required for readiness |
| `spin_orbit_treatment` | `none`, `scalar_relativistic`, `explicit`, `unknown` | Required; `unknown` blocks readiness |
| `total_magnetic_moment` | magnetic-moment `Quantity` per cell | Optional and experimental |
| `initial_site_moments` | unique `site_reference` plus scalar moment `Quantity` | Optional and experimental |
| `magnetic_ordering` | `nonmagnetic`, `ferromagnetic`, `antiferromagnetic`, `ferrimagnetic`, `paramagnetic`, `other`, `unknown` | Optional descriptive assertion |

Periodic states must not contain `charge`, `multiplicity`, or `electron_count`.
Net cell charge, compensating backgrounds, charged defects, electron reservoirs,
and grand-canonical conditions need an explicit later profile; they must not be
encoded as finite charge in alpha.

### Periodic invariants

- `target_reference` resolves to a `PeriodicStructure`.
- every initial site-moment reference resolves to exactly one site in the target
  structure, and no site appears twice.
- nonzero scalar site moments require `spin_treatment: collinear` and
  `orbital_treatment: unrestricted`.
- the alpha schema has no vector site-moment field. A non-collinear calculation
  requiring directional initial moments is not ready until a later schema
  defines an explicit vector and coordinate frame.
- `spin_orbit_treatment: explicit` requires `spin_treatment: non_collinear` for
  alpha readiness. An adapter with a reviewed alternative mapping may support a
  broader combination in a later profile.
- `spin_orbit_treatment: unknown` may preserve incomplete imported intent but
  blocks compute readiness.
- `magnetic_ordering: nonmagnetic` conflicts with a nonzero total or site
  moment.
- moment units, per-cell convention, coordinate frame for vectors, and target
  cell basis must be explicit before the field can participate in readiness.

`magnetic_ordering` is an assertion or label, not a value inferred solely from
initial moments. `paramagnetic` and `other` cannot become compute-ready without
a backend profile explaining their model. A backend may use initial moments as
initial conditions, but a converged result does not silently replace the
immutable requested state.

The validator must not apply finite electron-count parity, finite multiplicity,
or molecule formal-charge rules to a periodic state.

## State intent versus execution realization

The state records scientific intent at ChemIR level. The compute adapter maps it
to backend input under a versioned capability manifest and emits a loss report.
The resolved plan records exact generated input and backend conventions.

Examples of required mapping disclosure include:

- whether `restricted` maps to a non-spin-polarized backend mode;
- whether scalar moments are per atom, site, species, cell, or formula unit;
- how non-collinear vectors are oriented;
- which spin-orbit setting and relativistic approximation are used;
- whether the backend ignores `magnetic_ordering` after converting initial
  moments; and
- whether symmetry is reduced because of magnetic initialization.

An adapter cannot claim `SEMANTIC_EQUIVALENT_UNDER_PROFILE` unless every
required state field has a defined mapping within tolerance. Ignoring or
approximating one is `LOSSY_WITH_REPORT` and requires the loss policy from
RFC-0001.

## Calculation readiness

Readiness is profile- and backend-specific:

- finite core readiness requires a finite target, required charge and
  multiplicity,
  resolvable geometry when the task requires it, and parity validation when an
  electron count can be derived;
- a finite state with unavailable electron count may be preserved, but the
  backend profile decides whether it must block and must state why;
- periodic readiness requires an explicit three-dimensional periodic structure
  for core atomistic paths and all state fields required by the backend
  capability manifest;
- an average crystal cannot become atomistic compute-ready through this RFC;
  RFC-0004 governs materialization or explicit backend support; and
- a state outside an adapter's exact treatment matrix is unsupported rather
  than silently downgraded.

Only a successful readiness check can contribute to `COMPUTE_PLAN_READY`.
Readiness does not establish that the selected state or method is scientifically
appropriate.

## Diagnostics

| Code | Default severity | Condition |
|---|---|---|
| `ELECTRONIC_STATE_MODEL_UNKNOWN` | error | `model` is missing or unsupported |
| `FINITE_STATE_FIELD_MISSING` | error | Charge or multiplicity is absent from the core alpha state |
| `FINITE_STATE_PERIODIC_FIELD` | error | Periodic-only field occurs in a finite state |
| `FINITE_ELECTRON_COUNT_UNAVAILABLE` | warning | Complete derivation is not possible |
| `FINITE_ELECTRON_COUNT_NEGATIVE` | error | Derived count is negative |
| `FINITE_MULTIPLICITY_INVALID` | error | Multiplicity is not a positive integer |
| `FINITE_MULTIPLICITY_PARITY` | error | Complete electron-count parity is inconsistent |
| `FINITE_CHARGE_MODEL_CONFLICT` | error or review_required by completeness | Total charge conflicts with a declared model |
| `PERIODIC_STATE_FINITE_FIELD` | error | Charge, multiplicity, or finite electron count occurs in periodic state |
| `PERIODIC_SITE_MOMENT_REFERENCE` | error | Site reference is missing, duplicated, or targets another structure |
| `PERIODIC_SPIN_COMBINATION_UNSUPPORTED` | error at readiness | Treatment combination has no reviewed mapping |
| `PERIODIC_MAGNETIC_ASSERTION_CONFLICT` | review_required | Declared ordering conflicts with moment assertions |
| `ELECTRONIC_STATE_ADAPTER_LOSS` | review_required | Backend mapping drops or approximates state semantics |

An import-time incomplete state may carry warnings or `review_required` and
remain inspectable. The same condition becomes an error when the requested
calculation would be undefined.

## Canonicalization and provenance

All state fields participate in semantic canonicalization except explicitly
non-semantic evidence timestamps. Integer charge and multiplicity are exact.
Magnetic quantities use the versioned unit registry and decimal rules from
RFC-0001. Site-moment arrays are a schema-declared set sorted by site ID for
hashing; duplicate site IDs are rejected.

Derived electron count, derived magnetic interpretations, and toolkit-inferred
fields record producer, version, configuration, rule-bundle hash, evidence, and
applicability domain. Recomputing a derivation does not mutate the state; a new
evidence record and, if semantics changed, a new state are created.

Changing the state, target, derivation policy, or adapter mapping invalidates
dependent logical plans and approvals under RFC-0002.

## Conformance tests

### Finite core fixtures

1. Neutral singlet water: charge `0`, multiplicity `1`, ten electrons.
2. A supported odd-electron doublet: odd electron count and multiplicity `2`.
3. An ion with a complete atom inventory and consistent integer charge.
4. Missing charge and missing multiplicity retained in import evidence but
   rejected as a core alpha `ElectronicState`.
5. Negative electron count, zero multiplicity, parity mismatch, and complete
   formal-charge conflict as negative fixtures.
6. A coordination complex with complete and incomplete oxidation-state models,
   demonstrating error versus review behavior.

### Periodic experimental fixtures

1. Nonmagnetic silicon with restricted, collinear, `none` spin-orbit intent.
2. Collinear ferromagnetic cell with scalar initial site moments.
3. Non-collinear intent without directional initialization, plus a negative
   fixture proving that scalar site moments cannot stand in for vectors.
4. Finite `multiplicity` on a periodic state as a hard schema error.
5. Missing/duplicate site references and nonzero moments under restricted
   treatment as negative fixtures.
6. Adapter capability tests for exact, lossy, and unsupported mappings.

No periodic fixture counts toward normative core-v1 electronic-state support
until the periodic profile is separately qualified.

## Alpha decision register

Fixed for `v1alpha1`: `model: finite|periodic`; `target_reference`; required
finite `charge` in `[-128, 128]` and `multiplicity` in `[1, 128]`;
`orbital_treatment`, `spin_treatment`, and `spin_orbit_treatment` for periodic
states; omission rather than `null` for optional fields; exact finite parity
validation; and no finite rules on periodic systems.

Open items:

| Open item | Required resolution |
|---|---|
| Periodic profile status | Decide whether any periodic state subset joins core v1 or remains experimental after backend spikes |
| Magnetic units | Freeze scalar/vector moment units, per-cell conventions, axes, and canonical conversion |
| Orbital vocabulary | Validate `restricted`/`unrestricted` across QCEngine, ASE calculators, and chosen periodic backends |
| Spin-orbit vocabulary | Map `none`, `scalar_relativistic`, `explicit`, and preservation-only `unknown` to reviewed backend semantics |
| Net cell charge | Define charged-cell, background-charge, defect-charge, and reservoir semantics in a later profile |
| Excited states | Define state indexing, degeneracy, roots, and method-dependent meaning outside alpha core |
| Smearing and occupations | Decide which fields are scientific state versus calculation/backend settings |
| Pseudopotential electron count | Define derived electron evidence without confusing valence and total electrons |
| Charge/multiplicity bounds | Review the alpha defensive limits before beta without presenting them as universal chemistry maxima |
| Magnetic ordering | Decide whether the descriptive enum becomes a validated ontology or remains evidence-only |

## Acceptance criteria

RFC-0003 is implemented for alpha when:

- JSON Schema selects mutually exclusive finite and periodic branches by
  `model`;
- forbidden cross-model fields fail schema validation;
- finite charge, electron-count, and parity fixtures produce stable diagnostics;
- calculation planning fails closed when a required state is incomplete or the
  adapter mapping is unsupported;
- no periodic validation path invokes a finite multiplicity rule; and
- state-to-backend conversion emits a capability-bound loss report and exact
  resolved input evidence.

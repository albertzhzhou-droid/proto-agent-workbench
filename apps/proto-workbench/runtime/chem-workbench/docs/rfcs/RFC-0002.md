# RFC-0002: Claims, Typed Hashes, Attestations, and Approval Invalidation

**Status:** Draft for alpha implementation  
**Target:** Claim and evidence model `v1alpha1`  
**Last updated:** 2026-09-02  
**Decision owners:** Core, runtime, provenance, and review maintainers

## Summary

Chem Workbench represents status as a directed acyclic graph of narrowly scoped
claims. It does not use a single success flag. Every claim names its producer,
prerequisites, immutable evidence, and invalidation inputs. Approvals are
append-only attestations over typed hashes. A mismatch invalidates the approval
and all dependent claims; it never edits the approved object or silently
retargets the attestation.

This RFC defines the alpha ledger and verification rules. It does not claim that
signing, multi-user identity, or release-grade concurrent ledger storage is
already implemented.

## Goals

- Make parse, structural, computational, convergence, result, and review claims
  independently inspectable.
- Prevent process exit or parsed output from being presented as scientific
  correctness.
- Bind approvals to the exact intent and execution evidence that reviewers saw.
- Make invalidation deterministic, transitive, append-only, and auditable.
- Give CLI and desktop one shared claim verifier.

## Non-goals

- Establishing scientific truth, experimental feasibility, safety, or
  laboratory approval.
- Defining a public-key infrastructure or a legal electronic-signature policy.
- Treating SQLite state as the only copy of evidence.
- Allowing alpha components to issue laboratory or platform claims.

## Typed hash model

Hashes answer different questions and must not be stored in one untyped digest
field.

| Type | Input and meaning |
|---|---|
| `source_sha256` | SHA-256 of exact authored or imported bytes before parsing |
| `semantic_hash` | SHA-256 of canonical ChemIR semantic content under RFC-0001 |
| `artifact_sha256` | SHA-256 of exact serialized artifact bytes |
| `logical_plan_hash` | SHA-256 of portable lowered computation intent and capability requirements |
| `resolved_execution_plan_hash` | SHA-256 of the logical plan plus exact runtime resolution |
| `rule_bundle_hash` | SHA-256 of the validator/rule bundle and its applicability metadata |
| `capability_manifest_hash` | SHA-256 of the canonical adapter/backend capability manifest |
| `policy_hash` | SHA-256 of the canonical automatic or human approval policy |

Every hash value is lowercase hexadecimal SHA-256 in alpha. A record stores the
type and algorithm explicitly even when the field name appears specific:

```json
{
  "type": "semantic_hash",
  "algorithm": "sha256",
  "value": "0123456789abcdef..."
}
```

The typed record is an encoding and binding wrapper around a digest; it is not a
second hashing transform. Each digest type uses its type-specific construction.
In particular, `semantic_hash` uses the schema-, canonicalization-, and
normalization-bound formula in RFC-0001, while `source_sha256` and
`artifact_sha256` hash exact bytes directly.

Unless this RFC or another versioned specification defines a more specific
construction, a logical typed digest uses the default domain:

```text
SHA-256("chem-workbench:" || type || ":v1alpha1\0" || canonical_or_exact_bytes)
```

The default formula must not be applied again to an already constructed
`semantic_hash`, `source_sha256`, or `artifact_sha256`. The type remains
explicit in every containing record.

## Plan hashes

### Logical plan

The logical plan is portable between CLI and desktop. Its hash includes:

- the target ChemIR semantic hash;
- the `CalculationSpec` semantic hash;
- task, method, requested properties, and scientific convergence intent;
- basis-set or pseudopotential registry identity at the intent level;
- normalized units and deterministic lowering output;
- compute adapter identity, version, and lowering-schema version;
- required backend family and portable version constraints;
- required capabilities and the capability-manifest hash used while lowering;
- portable resource requirements and network policy; and
- every declared assumption or unresolved item that affects readiness.

It excludes absolute paths, selected machine resources, executable locations,
environment values, timestamps, and run identifiers.

### Resolved execution plan

The resolved plan includes the complete logical plan and additionally binds:

- `logical_plan_hash`;
- exact adapter package and backend executable or package digests;
- exact generated native input bytes or their artifact hashes;
- exact basis-set, pseudopotential, model, parameter, and required-file digests;
- the environment allowlist and the values actually passed;
- working-directory policy expressed without a host-specific absolute path;
- selected CPU, memory, time, output, and process limits;
- the enforced network policy;
- platform and architecture identity;
- runtime and capability snapshots; and
- the resolver and trusted-runner policy versions.

A resolved plan must not contain a secret. If a backend requires a credential,
the plan contains a credential-slot identifier and its policy, never the secret
value. Software-only v1 acceptance backends are expected to require no network
credential.

Canonicalization of both plans uses the same bounded decimal, map, and set
rules as RFC-0001 but a distinct plan schema and hash domain. Equal logical plan
hashes do not imply equal resolved environments. Equal resolved plan hashes
require all bound resolution data to match.

## Current pre-alpha review-packet boundary

The implemented `review/v1alpha1` packet is not the claim ledger defined below.
It is a closed-schema, unsigned self-consistency package containing typed source,
ChemIR semantic, and canonical ChemIR artifact digests. A packet produced
directly from `.chem` source may include one bounded `SOURCE_PARSE_ACCEPTED`
entry in its `observations` array, using `observation_type`, compiler identity,
typed source evidence, and no prerequisites. Every packet keeps `PARSE_VALID` in
`not_claimed`; the observation therefore cannot be mistaken for issuance of the
RFC claim. A packet created from an existing ChemIR artifact contains no such
observation because it did not re-execute the source parser.

The observation vocabulary is deliberately separate from RFC claims. An
observation is not a `claim/v1alpha1` record: it has no `claim_id`, claim-type
registry binding, ledger sequence, invalidation bindings, attestation, or
signature, and it must not be inserted into the claim DAG. `chem inspect`
verifies the packet schema and recomputes its permitted bindings, then reports
`verification_scope: self_consistency` and `signature_status: unsigned`; that
establishes only that those permitted bindings are internally consistent. Anyone
able to replace an unsigned packet can recompute all of those values, so
successful inspection is not proof of origin, authenticity, human review, or
approval.

## Claim record

A claim is an immutable assertion supported by evidence:

```json
{
  "claim_schema_version": "claim/v1alpha1",
  "claim_id": "claim:01H...",
  "claim_type": "COMPUTE_PLAN_READY",
  "subject": {
    "kind": "LogicalComputePlan",
    "id": "plan:water-single-point"
  },
  "producer": {
    "kind": "planner",
    "id": "org.chem-workbench.core-planner",
    "version": "0.1.0",
    "artifact_sha256": "..."
  },
  "prerequisite_claim_ids": ["claim:..."],
  "evidence_bindings": [
    {"role": "logical_plan", "type": "logical_plan_hash", "value": "..."}
  ],
  "invalidation_bindings": [
    {"role": "target", "type": "semantic_hash", "value": "..."}
  ],
  "issued_at": "2026-09-02T00:00:00Z"
}
```

`issued_at` is audit metadata and does not establish event ordering by itself.
Ledger sequence and prerequisite edges establish ordering. Clock rollback or an
untrusted local clock cannot make an otherwise invalid claim valid.

A claim is active only if:

1. its schema and claim type are known;
2. its record hash matches the immutable ledger entry;
3. the producer is allowed for that claim type under the active profile;
4. all required prerequisite claims exist and are active;
5. the prerequisite edges are acyclic and type-correct;
6. every required evidence and invalidation binding is present;
7. every currently resolved input equals its bound hash; and
8. no valid invalidation record targets it or one of its prerequisites.

Claims cannot be edited. A correction creates a new claim and, when necessary,
an invalidation record for the old one.

## Minimum claim DAG

Core validation claims are independent where their schemas permit:

```text
PARSE_VALID
STRUCTURE_MODEL_CONSISTENT
CHEMISTRY_CHECKED
RECORD_VALIDATED
```

The alpha computation path is:

```text
COMPUTE_PLAN_READY
-> COMPUTE_APPROVED
-> COMPUTE_RUNNING
-> PROCESS_EXITED
-> OUTPUT_PARSED
-> CONVERGENCE_VERIFIED
-> RESULT_VALIDATED
-> COMPUTE_RESULT_REVIEWED
```

`COMPUTE_FAILED` is a terminal failure claim that may be produced after
`COMPUTE_APPROVED` or any later runtime stage. Cancellation, timeout, launch
failure, non-acceptable exit, malformed required output, and resource-policy
termination use deterministic failure categories. `PROCESS_EXITED` records any
observed operating-system process exit and its status; it is not itself a
success claim and may coexist with `COMPUTE_FAILED`. A result parser may still
record `OUTPUT_PARSED` for a well-formed failure artifact, but an active failure
blocks `CONVERGENCE_VERIFIED` and later success-only claims.

The required producer and evidence rules are:

| Claim | Allowed producer | Minimum prerequisite and evidence |
|---|---|---|
| `PARSE_VALID` | Identified parser | Source hash, grammar version, diagnostics |
| `STRUCTURE_MODEL_CONSISTENT` | Profile validator | Parsed object, schema/profile versions, `PARSE_VALID` when source-derived |
| `CHEMISTRY_CHECKED` | Scientific rule bundle | Structure claim, rule-bundle hash, diagnostics and applicability domain |
| `RECORD_VALIDATED` | Record-profile validator | Record semantic hash, profile, diagnostics |
| `COMPUTE_PLAN_READY` | Planner | Consistent target, `CalculationSpec`, logical plan hash |
| `COMPUTE_APPROVED` | Human or named automatic policy | Active plan-ready claim, policy identity/hash, logical plan hash |
| `COMPUTE_RUNNING` | Trusted runner | Active approval, resolved plan hash, successful startup revalidation |
| `PROCESS_EXITED` | Trusted runner | Active running claim, observed exit status, bounded log hashes, raw artifact hashes |
| `OUTPUT_PARSED` | Result adapter | Active process-exited claim, raw hashes, parser identity/version, diagnostics |
| `CONVERGENCE_VERIFIED` | Task-specific validator | Active output-parsed claim, parsed result, criteria, units, validator and rule hash |
| `RESULT_VALIDATED` | Result-profile validator | Active convergence claim, required properties, ranges/tolerances, provenance completeness |
| `COMPUTE_RESULT_REVIEWED` | Human reviewer | Active validated-result claim and exact reviewed claim/artifact hashes |
| `COMPUTE_FAILED` | Planner, resolver, or trusted runner | Active latest applicable prerequisite, failure category, stage, available bounded evidence |

The literal prerequisite sets are maintained in a versioned claim-type
registry. A producer cannot weaken them in its own output.

`RESULT_REPRODUCED` is separate from the linear chain. It requires at least two
identified runs, a versioned repeat protocol, a comparison profile, comparison
output, and all relevant result and environment hashes. It is never inferred
from one run.

## Meaning boundaries

- `PARSE_VALID` means only that an identified parser accepted the bytes.
- `STRUCTURE_MODEL_CONSISTENT` means only that declared deterministic invariants
  under an identified profile passed.
- `CHEMISTRY_CHECKED` is bounded by its rule bundle and applicability domain.
- `PROCESS_EXITED` means the trusted runner observed an acceptable process exit
  under the resolved policy; it is not convergence or correctness.
- `OUTPUT_PARSED` means an identified parser interpreted required output.
- `CONVERGENCE_VERIFIED` means declared task-specific criteria passed.
- `RESULT_VALIDATED` is bounded by its result profile, units, expected ranges,
  tolerances, and provenance requirements.
- `COMPUTE_RESULT_REVIEWED` records review of exact evidence; it is not a
  universal scientific endorsement.

No alpha claim establishes experimental feasibility, chemical safety,
laboratory approval, or laboratory execution.

## Attestations and approvals

An attestation is an immutable record outside the approved ChemIR payload:

```json
{
  "attestation_schema_version": "attestation/v1alpha1",
  "attestation_id": "attestation:01H...",
  "attestation_type": "COMPUTE_APPROVAL",
  "subject_claim_ids": ["claim:..."],
  "bindings": [
    {"role": "source", "type": "source_sha256", "value": "..."},
    {"role": "chemir", "type": "semantic_hash", "value": "..."},
    {"role": "logical_plan", "type": "logical_plan_hash", "value": "..."},
    {"role": "resolved_plan", "type": "resolved_execution_plan_hash", "value": "..."},
    {"role": "capabilities", "type": "capability_manifest_hash", "value": "..."}
  ],
  "issuer": {"kind": "human", "id": "local-reviewer-slot"},
  "policy": {"id": "bounded-local-compute-alpha", "hash": "..."},
  "issued_at": "2026-09-02T00:00:00Z",
  "signature": null
}
```

The binding set is profile-defined. A compute approval binds at minimum source,
ChemIR semantic content, logical plan, resolved plan, adapter version/package,
backend version/package, capability snapshot, and approval policy. If approval
occurs before environment resolution, the logical approval is a separate
attestation and a second resolution authorization is required before launch;
the implementation must not pretend an unresolved plan hash binds an executable.

Human identity is a local trust assertion in alpha until a signature and key
policy is selected. A null signature must be displayed as `UNSIGNED_LOCAL`; it
must not be presented as cryptographically verified.

A named automatic policy may approve only a bounded local computation. Its
attestation records the policy identifier, policy hash, decision inputs, and
limits. No automatic policy can approve a laboratory path.

## Invalidation

Invalidation is append-only. The verifier compares each binding with current
immutable evidence immediately before a dependent action. A mismatch writes:

```json
{
  "invalidation_schema_version": "invalidation/v1alpha1",
  "invalidation_id": "invalidation:01H...",
  "target_claim_or_attestation_id": "attestation:01H...",
  "reason_code": "BOUND_HASH_MISMATCH",
  "expected": {"type": "resolved_execution_plan_hash", "value": "..."},
  "observed": {"type": "resolved_execution_plan_hash", "value": "..."},
  "detected_by": "trusted-runner",
  "detected_at": "2026-09-02T00:00:00Z"
}
```

At minimum, a change to source, ChemIR, schema, canonicalization profile,
normalization profile, validator/rule bundle, adapter, backend, generated native
input, basis or pseudopotential, capability manifest, approval policy,
environment policy, resource resolution, platform snapshot, or reviewed
artifact invalidates every dependent claim and approval.

Invalidation propagates by graph reachability from the changed binding or
invalidated claim. The verifier recomputes active state; it does not copy an
`invalidated` flag into every historical claim. A cached active-state index is
discardable and must be reconstructible from portable records.

An invalidated approval cannot be repaired by replacing its hashes. The user or
policy reviews the new evidence and issues a new attestation. Historical failed
and interrupted runs remain available but cannot acquire success-only claims.

## Ledger and concurrency

Portable JSON or JSONL records plus exact artifact files are authoritative. A
SQLite database may index them and support recovery, but it is not the sole copy
of scientific evidence.

Each ledger append must:

1. validate the record and all referenced IDs;
2. acquire a cross-process append lock;
3. verify the previous sequence and record hash;
4. append one complete length-bounded record and flush it durably;
5. update the recoverable index; and
6. release the lock.

The alpha format must detect truncation, duplicate IDs, sequence gaps, and a
record whose stored hash does not match its bytes. Recovery may discard only an
incomplete final frame and must report that action. It may not rewrite earlier
records.

## Public provenance

`LOCAL_FULL` may contain bounded local identities, paths, and logs needed for
debugging and replay. `PUBLIC_SANITIZED` is rebuilt from an allowlist and
excludes absolute paths, user and host identity, operator identity, logs,
credentials, cache state, staging state, and other machine-specific metadata.

Sanitization does not change or reuse a local attestation as though the public
record were byte-identical. The export creates a new manifest with its own
artifact hash and records redaction/projection provenance. Scientific-data
rights and software licenses remain explicit.

## Required verification errors

| Code | Condition |
|---|---|
| `CLAIM_TYPE_UNKNOWN` | Claim type is absent from the active registry |
| `CLAIM_PRODUCER_UNAUTHORIZED` | Producer is not permitted for the claim type |
| `CLAIM_PREREQUISITE_MISSING` | Required predecessor is missing or inactive |
| `CLAIM_DAG_CYCLE` | Prerequisite edges contain a cycle |
| `CLAIM_EVIDENCE_INCOMPLETE` | Required typed binding is absent |
| `ATTESTATION_UNSIGNED_LOCAL` | Attestation is local and has no verified signature |
| `APPROVAL_STALE` | Any bound hash, policy, or prerequisite no longer matches |
| `BOUND_HASH_MISMATCH` | Exact expected and observed typed digests differ |
| `LEDGER_INTEGRITY_FAILURE` | Record hash, framing, sequence, or uniqueness check fails |
| `LAB_CLAIM_FORBIDDEN` | An alpha or software-only component attempts a laboratory claim |

## Security requirements

- Verification fails closed on unknown claim, policy, hash, canonicalization,
  or signature versions.
- A claim record cannot authorize its own producer or define its own required
  prerequisites.
- The current system clock cannot override hash, sequence, or prerequisite
  failures.
- Secrets are never included in a plan, claim, ledger event, bounded log, or
  public export.
- User-visible views show inactive, invalidated, unsigned, partial, and
  unresolved states explicitly.
- The runner verifies approval and resolved bindings immediately before launch,
  as specified by RFC-0005.

## Conformance tests

The alpha suite includes:

1. Golden typed-hash vectors and domain-separation checks.
2. CLI/desktop equality for semantic and logical-plan hashes.
3. Resolved-plan equality only under the same frozen environment profile.
4. Valid and invalid claim DAG fixtures, including cycles, wrong producer,
   wrong prerequisite type, missing evidence, and duplicate claim IDs.
5. A mutation matrix changing each bound source, schema, rule, adapter,
   executable, input, policy, environment, resource, and artifact field.
6. Transitive invalidation across every successor edge.
7. Proof that invalidated records remain inspectable and cannot be edited back
   into active state.
8. Concurrent append, interrupted append, truncated tail, and index-rebuild
   tests.
9. Clock rollback and future timestamp tests that do not bypass verification.
10. Public export tests that remove local identity while preserving rights,
    licenses, claim meaning, and export provenance.

## Alpha decision register

Fixed for `v1alpha1`: typed SHA-256 hashes; domain-separated semantic and plan
hashes; immutable claim records; a versioned claim-type registry; append-only
attestations and invalidations; transitive active-state evaluation; and no
laboratory claims.

Open items that must be decided before schema beta or the stated milestone:

| Open item | Required resolution |
|---|---|
| Signing profile | Select signature envelope, key identifiers, verification libraries, revocation, and offline behavior |
| Local human identity | Define enrollment, display, privacy, and export rules; alpha remains `UNSIGNED_LOCAL` without signatures |
| Ledger framing | Freeze canonical JSON versus length-prefixed JSONL and crash-recovery semantics |
| Automatic approval | Freeze allowed calculation bounds, policy inputs, expiry, and UI disclosure |
| Time authority | Decide whether signed timestamps are needed; never use wall time as sole ordering evidence |
| Plan schemas | Freeze portable resource vocabulary, environment representation, and capability snapshot fields |
| Rule-bundle identity | Define package layout and how scientific basis, reviewer, scope, and counterexamples are hashed |
| Reproduction claim | Freeze repeat protocol and numerical comparison profiles per backend/task |

No release-qualified approval claim may depend on an unresolved item needed for
its verification.

## Acceptance criteria

RFC-0002 is implemented for alpha when:

- one shared verifier reconstructs active claims from portable immutable
  records;
- the water calculation fixture can produce the claim path through the highest
  evidence-supported stage without skipping prerequisites;
- changing any bound logical or resolved input blocks launch or downstream
  review and emits a specific invalidation record;
- the UI and CLI never summarize `PROCESS_EXITED`, `OUTPUT_PARSED`, or
  `CONVERGENCE_VERIFIED` as scientific correctness;
- concurrent ledger writes cannot mix, overwrite, or silently truncate records;
  and
- no alpha registry contains platform or laboratory claim types.

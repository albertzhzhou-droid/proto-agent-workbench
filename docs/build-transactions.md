# Workbench build transactions

The maintained Windows desktop, renderer, development-desktop, icon, template, sidecar, and release entrypoints share `build/locks/project-build.lock`. A live exclusive file handle owns the lease. Nested scripts can reuse only an explicit live lease in the same PowerShell process. Another process fails immediately; an environment variable cannot grant ownership. Development desktop holds its lease until its process exits.

Release packaging captures an allowlisted repository input tree and installed Node dependencies into a private directory. Files are copied rather than hardlinked. pnpm junctions are recreated inside the copied dependency tree; links to external inputs are rejected. The snapshot preserves uncommitted source bytes and records relative paths, sizes, hashes, directory identities, and dependency-link targets. Generated outputs and generated workspace-template copies are separate from their source inputs.

Candidate evidence uses `apps/proto-workbench/build/i-<full GUID>`, while the independent private repository uses the shallower `build/<same full GUID>`. The installed NSIS template resolver determines its projected working directory before copying and its actual private working directory before Electron Builder. Both must stay inside the copied dependency boundary and be at most 240 characters. Every template/include file and configured or standard fallback resource path is also checked against the 259-character Windows file-path bound; the actual path inventory must match the projection. A preserved Windows failure showed that a real 261-character working directory caused primary `ENOENT` and secondary output-pipe `ENOTCONN` errors before the compiler acquired a PID. A separate equal-byte compile-only comparison demonstrated that NSIS could launch from a shorter directory but still failed to open a 261-character include path. The current layout projects a 215-character cwd and longest template path of 257 characters, and rejects future path growth before an expensive build. No shared dependencies, extended-path aliases or weaker integrity checks are introduced.

pnpm 11 also records an absolute `virtualStoreDir` inside `.modules.yaml`. The package flow changes that one field only in the copied metadata so Electron Builder's package-manager dependency discovery resolves into the private `.pnpm` directory. It records a source-to-private transformation receipt and a separate derived input manifest, then rehashes the entire private tree. The original manifest and original dependency metadata remain unchanged. Maintained build commands invoke the private Node tools directly, and Electron Builder receives `npmRebuild=false`, which skips its install/rebuild path before the `beforeBuild` hook. No `install`, `install-app-deps`, or `rebuild:native` command is part of this transaction.

Sidecar compilation, workspace synchronization, desktop compilation, manifest generation, and Electron Builder run from that private tree. The package flow verifies copied inputs, original inputs, application payloads, runtime manifests, and the final published release tree. Source drift before or during publication blocks the transaction and restores the previous release. Existing dependencies are copied without an implicit native rebuild or install; a compatible native dependency installation is a prerequisite.

Standalone development builds remain serialized builds of the working tree. A release build uses private inputs. `scripts/build-native-qa.ps1` produces a separate development source/output snapshot and a `desktop-build.json` report for owned native QA. This initial QA profile references the existing dependency tree, which must remain unchanged during the build; its report explicitly records that limitation. It does not produce an installer or certify release isolation.

The transaction is not a hermetic Windows build. Node/Python executable hashes are recorded for release builds, while the external Python environment, Windows SDK, signing services, and installer tool caches remain external toolchain dependencies. A full staged release and native launch gate must validate Windows path lengths, native dependency compatibility, sidecar execution, and packaged interoperability. Focused lock/copy tests alone do not close that gate.

Input snapshots and their manifests are retained under the build evidence namespace for diagnosis. They contain installed dependencies and may be large; retention should be managed deliberately after verification. Do not upload local input snapshots. Direct invocation of underlying build tools outside the maintained entrypoints is outside the cooperative locking contract.

Use `scripts/package-win.ps1 -CandidateOnly` to retain setup/portable candidates and `release-candidate.json` under build staging without replacing the prior local release. The candidate report binds the source-input manifest, source tree, built payload, module manifest, ASAR, distribution EXEs, release tree, and Node/Python/archive-tool hashes. Authenticode inspection records each EXE's actual status and certificate thumbprints; it does not establish Windows reputation or SmartScreen acceptance.

Both distribution EXEs are extracted into fresh evidence directories without running the installer. Technical archive listings reject traversal, links, colliding Windows paths and excessive expansion. Each extracted application must match the entire already verified unpacked file tree, including the exact file set. Installer OS integration (shortcuts, registry, upgrade and uninstall) remains a separate gate. The candidate report explicitly records native smoke as pending, with exact unpacked and Portable executable paths. Payload verification alone does not claim successful application launch.

The NSIS installer retains the production AppId/GUID when its installation directory is changed. It still reads and writes the shared installation/uninstall records, uses shared shortcut names and updater cache, and can invoke an existing matching uninstaller or stop a process by executable name. A build-owned `/D` destination is therefore insufficient to isolate installer OS integration. Run the unchanged candidate installer in a disposable Windows environment for that gate; changing the installer identity would validate a different configuration. The application-only `--session-root` option does not alter NSIS registry, shortcut, cache, upgrade, or process behavior.

The current verification environment has no available disposable Windows VM or ready Windows Sandbox. Installer installation, upgrade and uninstallation validation is therefore unavailable here. No host installation or Windows feature enablement is part of the candidate workflow; Portable and extracted-payload smoke results must retain that explicit limitation.

Full input capture uses eight concurrent file operations, at most 8 MiB buffered per small file (larger files stream), and independent copied bytes. The final whole-tree destination pass replaces a redundant immediate per-file destination hash. Both the original source and final private tree must still match the initial manifest, including dependency link targets. All owned copy/hash tasks settle before a failed capture releases its lease. Do not substitute the development QA profile for this release capture.

After the final source freeze, run from the application directory:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/package-win.ps1 -CandidateOnly
```

The archive tool must be a full NSIS-capable `7z.exe` or `7zz.exe`; supply its exact path with `-ArchiveTool`, or use an existing `7z.exe` in PATH or the standard Program Files location. Preflight probes the actual decoder inventory before capturing inputs. Electron Builder's limited `7za.exe` can build the nested archives but cannot decode NSIS containers and is rejected. This command does not download or install a missing verifier. Other prerequisites are the installed compatible Node dependencies, project Python environment with PyInstaller, available NSIS toolchain, sufficient disk space for the independent input copy plus two extracted application payloads, and final Python/JavaScript/native QA evidence for the frozen source revision.

An owned native smoke pass must use a new profile and workspace under the QA evidence namespace and bind its report to the candidate EXE and ASAR hashes. The supported [`--session-root` option](isolated-desktop-sessions.md) binds both directories and skips default Documents workspace seeding; `--user-data-dir` alone is insufficient. Source tests cover the explicit bootstrap boundary. Actual packaged smoke must additionally observe the runtime profile/workspace paths, a real window, module-integrity success, a response from the packaged MCP sidecar, clean shutdown and logs. No model loading is part of this smoke gate. `verify-packaged-ui.mjs` is an older model-loading stress harness and is not the candidate smoke entrypoint. Never reuse the user's normal profile or claim installer integration from extracted payload execution.

The maintained no-model candidate driver is `scripts/verify-packaged-scientific.mjs`, using `scripts/owned-packaged-electron.ps1` for exact Portable-wrapper or verified installer-payload launch. It retains the production security fuses: no Node inspector is requested. The helper binds CIM creation to a retained process handle, verifies the actual EXE and ASAR hashes, and requires a Chromium child with the isolated profile before the driver interacts with the renderer. The driver independently checks the actual ASAR renderer URL, workspace settings, module manifest, new profile database, scientific exports and bundled sidecar preview. Standard streams and process cleanup are bounded; forced fallback, nonzero exits, remaining owned children and cleanup errors cannot count as a successful smoke pass. Profile/TEMP fixtures, owner records and reports remain in the controlled native QA evidence directory.

The 2026-09-04 preparation extracted official 7-Zip 26.03 into `build/tools/7zip-26.03/bin/7z.exe` using `scripts/prepare-archive-verifier.py`. It read the official MSI database and embedded CAB without executing installation. `build/tools/7zip-26.03/archive-tool.json` records the official release URL, published/downloaded SHA-256 match, executable/library hashes and extraction method. The MSI, EXE and DLL are `NotSigned`; the separately recorded Authenticode inspection does not claim a publisher signature. This tool is local build evidence, not an application dependency or distributed installer resource.

The read-only full installed-dependency hash benchmark recorded 42,989 entries and 861,184,599 bytes in 34.410 seconds in `build/upgrade-20260904/package-dependency-hash-timing.json`. This is a single source hashing pass, not a measured full release copy or package build. The focused packaging checks also use two real NSIS containers with explicitly toy application bytes; those fixtures are never executed and do not substitute for the real candidate launch gate.

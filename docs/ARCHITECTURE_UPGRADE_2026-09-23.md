# Architecture upgrade implementation record — 2026-09-23

This records the implementation following [the initial architecture review](ARCHITECTURE_REVIEW_2026-09-23.md) and the subsequent F1–F11 review supplied in `Pasted text.txt`. The two reviews reuse finding numbers: **CS1–CS8 below refer to the initial implementation sequence; F1–F11 refer to the subsequent review.** The documents supplied findings and proposed acceptance criteria; they were not independent authorization to change deployment, trust or scientific scope.

The implementation follows the review's incremental architecture A, including the recommended journal-first dual-read transition. The proposed append-only event store in architecture B remains a future migration.

The work improves execution contracts, recovery, evidence display and local software verification. Final Node and Python base validation, typechecking, offline verification and desktop source bundling passed with the explicit environment skips recorded below. This does not establish scientific validity, successful live-model or GPU inference, installer readiness, or a completed migration to a single event store.

## User-facing recovery and evidence

Open **Workspace execution journal** using the history icon in the topbar. The default filter shows operations needing effect review; select a surface or clear the filter to inspect terminal records. Select a record to inspect its tool identity, argument hash, decision and receipt. For an unknown effect, enter the reviewer and a workspace-relative evidence file, then record either effect confirmed or no effect confirmed. The host checks the file and records `path#sha256=<digest>` with the verdict. A finalized operation ID is not automatically dispatched again.

The local source preview uses the production workspace journal through a same-origin development route. Retained UI acceptance demonstrates a synthetic unknown Compute operation, rejection of missing evidence, a checked no-effect verdict and reopening that verdict. Separate automated acceptance copies the workspace `build` directory to a second profile fixture and verifies the same record and evidence hash there. These are software recovery checks; no worker or model is launched for the synthetic reconciliation fixture.

The preview was checked at desktop size and at 390 × 844. The mobile recovery record reports document width 390, dialog width 352 and dialog scroll width 341, with no horizontal overflow. The earlier Chemistry preview also preserves successful and invalid-formula paths, their artifacts, and distinct journal outcomes. UI evidence is under [build/architecture-upgrade-20260923](../build/architecture-upgrade-20260923/), including `ui-acceptance.json` and `ui-recovery-acceptance.json`. That preview does not substitute for a packaged desktop or clean-machine test.

Chat now distinguishes **Blocked**, **Incomplete evidence** and a finished response. Receipt cards keep unavailable numeric values visible with a reason rather than silently dropping them or inventing units. Model interpretation remains labeled unreviewed.

## Operational limits

- The workspace journal is supported under one owning host process. Simultaneous independent host processes sharing the same journal are not supported; the current orphan-detection/lease model is not a distributed coordinator.
- Recovery records uncertain effects; it does not provide exactly-once execution. Effects may occur before a receipt is persisted. A new operation ID can repeat a real external effect and requires deliberate review.
- Legacy operation tombstones without a matching verifiable historical row remain blocked. Recovery cannot fabricate a journal record or receipt to make such an identity replayable; restoring trustworthy historical state is a separate boundary.
- Migration/checksum and artifact-version routing preserve or reject data; they do not establish source trust. The existing trust subsystem, governance checks, materialization eligibility and review requirements were not redesigned.
- Quantity coverage is explicitly partial: two bound producers and 125 exemptions. Numerical-reference or implementation maturity, software completion, receipt integrity and scientific validity remain separate claims.
- The process-tree guarantee is unverified on this containment host because its negative control cannot distinguish the implementation under test. The skip is retained in totals.
- This is source and local software-validation work. No model/GPU inference, installer release, physical laboratory workflow or production deployment is included.
